# CopilotBYOKManager 推广计划

目标是找到真正需要“同一 Provider 配置复用于多个 Copilot 客户端”的开发者，验证首次配置是否顺畅，再扩大传播。**先完成发布门槛，再宣传对应能力；本计划不授权发帖、联系用户、投放广告或购买服务。**

当前可以准备素材、提供标明模拟数据的浏览器试用和征集自愿反馈；还不能宣布正式安装版上线。首次公开版本的条件见[发布标准](release-criteria.md)，能力与缺口见[实现状态](implementation-status.md)。

2026-10-14 当前界面收敛为 **总览 / 供应商 / 应用 / 关于**，并提供中英文、浅色/深色/跟随系统和 Windows 关闭至托盘的实现。用量、账单、独立 GitHub 授权、资源和统一活动页暂不开放；已有实现与数据保留，见[功能记录](feature-availability.md)。本轮演示和宣传只覆盖四页配置主流程，托盘仍需实际操作验收，不把隐藏功能作为现版卖点。

## 1. 先服务谁

首批目标是 Windows 上交替使用 VS Code、Copilot CLI 和受支持 JetBrains IDE 的个人开发者。他们已有自己的模型供应商，反复维护端点、密钥与模型列表，希望集中管理又不破坏已有客户端配置。

第二批是帮助同事配置开发环境的开源维护者和小团队技术负责人。产品仍是本机、单用户工具，不承诺团队同步、统一账号授权、组织账单或企业管理。

暂不面向只用一个原生供应商、只需要代理网关，或希望绕过 Copilot 登录、订阅、组织策略的人群。宣传不把它包装成模型代理、免费额度工具或 GitHub 官方产品。

## 2. 固定主张与证明

中文主张：**Provider 一次配置，多端 Copilot 复用。**

English positioning: **Configure a provider once. Reuse it across your Copilot clients.**

必要副说明：管理端点、密钥和模型，预览后发布到 VS Code、Copilot CLI 与已审核版本的 JetBrains。Copilot App 使用手动指引。各客户端仍需自己的官方登录和模型选用。

| 主张 | 展示证据 | 不得暗示 |
| --- | --- | --- |
| 一次维护、多端发布 | 只编辑一次连接，预览多个目标，再核对实际客户端模型 | 一键共享官方登录、所有客户端自动选中模型 |
| 可审核、可撤销 | 展示目标预览、受管范围、保留其他供应商、撤销及外部冲突拒绝 | 任意变更都能无条件回滚 |
| 本地管理 | 说明 OS 凭据库、目标客户端需要的本地密钥配置、隐私边界 | 密钥永远不写磁盘、客户端配置天然加密、绝对不会泄露 |
| 用量更清楚（延期，不用于现版推广） | 重新开放且对应验收通过后，才分别展示官方配额、个人账单、本地观察和 API 等价估算 | 本版已有可用用量页、全量账单、提供商实际收费、组织用量、未知就是零 |
| 中英文可用 | 同一主流程的中英截图与切换演示 | 第三方诊断、用户输入或上游模型名也被翻译 |

竞品比较只围绕已验证的任务差异，避免“最强”“唯一”“全兼容”。如果需要与 CC Switch 等工具比较，另做同版本、同客户端和同操作的对照验证后再写，不凭印象声称优劣。

| 产物 | 内容与验收要求 |

## 4. 分阶段执行

以下以发布门槛通过日为起点，是执行顺序，不是已承诺日期。维护者负责技术与发布审核；内容编辑负责双语素材；社区联系人负责规则复核和答疑。可以由同一人担任，执行前明确当天谁值守。

| 阶段 | 行动 | 进入下一阶段的条件 |
| --- | --- | --- |
| 准备期 | 完成素材包、反馈模板和安装入口；审查各渠道当日规则；邀请已有联系且自愿参加的测试者 | 素材无越界承诺；隐私审阅通过；有可试用版本和可用反馈入口 |
| 候选版第 1 周 | G0–G7 通过后，经维护者批准发布 RC；邀请 5–10 名目标用户，每人按清单完成一条主流程；逐个记录卡点 | 达到 G8；无未解决 P0/P1；常见问题可由手册解答 |
| 正式发布日 | 首次稳定版通过后，先发布 GitHub Release 和双语说明，再在一个中文渠道与一个英文渠道发帖；当天留出答疑时间 | 下载、安装和反馈入口正常；确认没有新增高严重度缺陷 |
| 发布后第 2–7 天 | 回复问题、复现失败、补齐 FAQ；发布一篇具体使用教程，而不是重复相同广告 | 问题有负责人、级别和状态；只扩散已经验证的使用路径 |
| 发布后第 2–4 周 | 汇总自愿反馈；优先修复配置失败与版本误判；按实际改进更新演示，再决定是否扩大渠道 | 有真实主流程完成证据；维护者能承接支持；不以星标数替代质量 |

## 5. 渠道顺序与内容

1. **GitHub 是主入口。** Release、支持表、用户手册和 Issues 保持一致。是否启用 Discussions 由维护者选择；不要为推广批量创建无关 issue 或 PR。
2. **中文首站候选：V2EX 的“分享创造”或掘金的实操文章。** 主题是“维护一份 Provider，给 VS Code / CLI / JetBrains 复用”，配任务演示、限制和反馈问题。发帖当天先检查版规和节点范围，不假定当前允许自推广。
3. **英文首站候选：Show HN。** 提供可以直接试用的成果、做它的原因和技术边界，由作者在场回答；不是只放预约表或宣传落地页。不要组织点赞。依据 [Show HN 官方规则](https://news.ycombinator.com/showhn.html)。
4. **Reddit 作为后续候选，不群发。** 只在主题匹配且明确允许自推广的社区发一篇针对性介绍，披露作者身份；不确定时先联系版主。平台规则之外还要遵守社区规则，参见 [Reddit Spam 规则](https://support.reddithelp.com/hc/en-us/articles/360043504051-Spam)。
5. **个人社交账号和现有开发者群。** 分享实际工作流、版本支持表和问题清单，不抓取成员名单、不批量私信、不冒充用户评价。需要发帖或邀请时另行确认文本、渠道与范围。

首月默认付费投放预算为 **0**。签名、域名、托管与广告均不自动采购；若后续提出预算，应先给出用途、金额上限、衡量方式和停止条件。

## 6. 如何衡量是否值得继续推广

首月先验证质量，以下为试验目标，不是预测或已取得结果：

| 指标 | 记录方式 | 起始目标 / 决策 |
| --- | --- | --- |
| 有效试用 | 用户自愿报告系统、客户端及完成步骤；不要求个人身份 | 首轮 5–10 人，覆盖中英文和至少两类客户端 |
| 主流程完成率 | 无需维护者代操作完成“添加→预览→发布→客户端选用→撤销”的人数 / 实际开始该流程的人数 | RC 至少 5 人开始，完成率至少 80% 且不少于 4 人完成；失败样本保留，不只统计成功者 |
| 首次配置用时 | 经同意的任务观察；把下载、编译、官方登录等待单独记下 | 记录中位数与最大值，连续两轮降低卡点；不预先承诺“30 秒完成” |
| 跨端收益 | 自愿报告同一连接确实用于两种客户端的人数与具体路径 | 至少 3 个独立、经核对的成功案例后，才把跨端演示作为主要传播素材 |
| 安全和可靠性 | P0/P1 数量、复现率、恢复结果 | 未解决 P0/P1 为 0；出现即暂停扩散 |
| 支持负担 | 问题到首次人工响应的时间、重复问题类型 | 工作日争取 48 小时内回应，不承诺未安排值班的全天 SLA |
| 传播参考 | 仓库聚合访问、Release 下载量、自然星标与有效反馈数 | 只作趋势参考；下载不是活跃用户，星标不是成功使用 |

不为本计划新增默认遥测、设备指纹、供应商密钥采集或对话上传。需要更细分析时先设计最小数据与用户同意机制，再另行评审。反馈整理只保留用户主动提供的必要元数据。

## 7. 发帖前检查与停止规则

- 对应 Release 真的存在，下载链接可访问，发布说明明确 RC 或稳定版。
- 三类自动客户端的宣传范围与该版本的真实验收相符；App 手动限制和 JetBrains 固定版本没有藏在页尾。
- 中英文主张一致，没有“免登录”“免费官方额度”“全客户端全版本支持”等误导。
- 截图与视频均经过隐私检查；“配置成功”与“请求成功”分别呈现。
- 发布者身份、反馈入口和当天答疑负责人明确；符合渠道当日规则。
- 维护者已批准实际发送，而不只是批准制定计划。

出现密钥风险、错误写入、数据丢失、安装阻塞或明显误导，立即暂停推广，按[发布标准](release-criteria.md#4-缺陷与停止条件)处理。支持能力不足时缩小招募规模，不继续扩大曝光。

规则核对日期：2026-10-13。候选渠道、指标和阶段安排是本项目的执行建议，不表示已经获得平台许可或已经上线。
